# Estimoto + API v1

All customer routes require `Authorization: Bearer <Supabase access token>`. JSON uses snake_case. Unknown fields are rejected on writes. Errors use `{"detail":"customer-safe explanation"}`. A definitive provider rejection before request creation adds `"code":"request_not_created"` with HTTP409; clients may clear that rejected operation. That rejection is a durable terminal outcome for the customer/key/body, including after provider eligibility changes. The same applies to request rejection for an unavailable owned vehicle or invalid saved ZIP. Creation and rejection decisions serialize through a customer-row database lock; delayed same-key calls cannot convert a rejected operation into a request or classify an existing request as not created. Changing the body for a previously used key conflicts. An unclassified409/idempotency conflict or transport failure must retain its pending retry identity. All IDs are opaque strings and every private lookup enforces authenticated ownership.

`GET /v1/bootstrap` returns an object with `profile`, `vehicles`, `providers`, `estimates`, `repairs`, `requests`, `reminders`, and `capabilities`. Each collection is an array. Capabilities includes `live_requests`, `live_estimates`, `carfax`, `youtube_search`, `demo` booleans plus `required_estimate_photo_keys` and `pdr_damage_panel_types` arrays. The client must not infer live capabilities from the presence of sample rows.

Profile: `id`, `email`, `name`, `phone`, `postal_code`, `contact_preference` (`email` or `phone`). `PUT /v1/profile` accepts name, phone, postal_code, contact_preference.

Vehicle: `id`, `nickname`, `year`, `make`, `model`, `vin`, `mileage`, `insurer`, `policy_number`. `POST /v1/vehicles`, `PUT /v1/vehicles/{id}`, `DELETE /v1/vehicles/{id}`. Required fields: year, make, model; defaults: empty strings, mileage 0. Deletion of referenced vehicles returns 409.

Provider: `id`, `name`, `kind` (`shop` or `technician`), `specialties` (array of `pdr`, `collision`, `maintenance`, `mechanical`), `postal_codes` (array of exact supported postal codes), `city`, `address`, `phone`, `mobile_service`, `accepting_requests`, `description`. `GET /v1/providers?specialty=pdr&postal_code=80202&mobile_only=true`. Only public opted-in providers appear; no fuzzy radius represented as exact distance.

Request: `id`, `vehicle_id`, `provider_id`, `specialty`, `description`, `preferred_time`, `status`, `delivery_status`, `created_at`, `updated_at`, `scheduled_at` (nullable ISO datetime), `events` (array of {status, message, created_at}). `POST /v1/requests` accepts vehicle_id, provider_id, specialty, description, preferred_time, share_contact (must be true). Requires `Idempotency-Key`; POST /v1/requests/{id}/cancel cancels when permitted. GET /v1/requests lists only owned requests. Live requests require a configured delivery bridge and a saved, normalized five-digit service ZIP within the provider’s published coverage. Retries with the same key/body return the original request; changing the body conflicts.

Estimate: `id`, `vehicle_id`, `discipline` (`pdr` or `collision`), `description`, `claim_number`, `date_of_loss`, `status` (`draft`, `submitted`, `reviewing`, `ready`, `approved`), `amount_cents` (nullable integer), `provider_name`, `provider_id` (nullable), `delivery_status` (`draft`, `queued`, `failed`, `delivered`), `processing_state` (`not_started`, `pending`, `processing`, `failed`, `complete`), `processing_error` (nullable safe text), `updated_at`, `photos` (array of {id, label}). `POST /v1/estimates` creates a draft, required vehicle_id/discipline/description (at most 2000 characters) and optional claim_number/date_of_loss. `POST /v1/estimates/{id}/photos` multipart file + label uploads or replaces a private JPEG/PNG/WebP with size/type validation; `GET /v1/estimates/{id}/photos/{photo_id}` requires the customer's bearer token. The eight required labels are `odometer`, `engine_bay`, `interior`, `tire_tread`, `front`, `driver`, `rear`, `passenger`. PDR additionally needs at least one `panel_<type>` label from the `pdr_damage_panel_types` capability; this is evidence for the original assessor, not a quoted pricing row. Collision may include `damage_close` and `damage_far`. Photo storage is capped per customer and uploads/submits have database-backed hourly rate limits.

`POST /v1/estimates/{id}/submit` accepts `{"provider_id":"<Plus provider id>","share_contact":true}` plus `Idempotency-Key: estimate:<id>` (any stable nonempty key up to 200 characters is accepted). The server requires an owned draft, saved name and reachable phone of at most 40 characters with at least seven digits, saved valid ZIP, a visible opted-in accepting **shop** with matching discipline and ZIP, all required private files, and the additional PDR damage photo. Receiver-compatible vehicle fields are checked before queueing: year 1950..2050, make/model 1..60 characters, nonempty VIN exactly 17 permitted characters, mileage 0..9,999,999, and claim number at most 60 characters. The server freezes the customer-approved contact, vehicle, provider, service ZIP, and SHA-256 photo manifest in one transaction with a durable outbox row. Successful same-key/body retries return the same estimate; a changed key/body after submission returns 409. `status=submitted` means the customer submitted to Plus; `delivery_status` separately shows upstream delivery. No amount is shown until an authoritative original-Estimoto snapshot supplies it. Photo uploads are locked after submission.

Repair: `id`, `vehicle_id`, `provider_name`, `title`, `status`, `updated_at`, `estimated_completion` (nullable ISO date), `stages` (array of {title, status: completed/current/upcoming, date: nullable ISO date}). Supplied only by the authenticated bridge.

Reminder: `id`, `vehicle_id`, `title`, `due_date` (nullable YYYY-MM-DD), `due_mileage` (nullable integer), `completed` (boolean). POST /v1/reminders creates a reminder (at least one due field required); POST /v1/reminders/{id}/complete completes it.

`POST /v1/assistant` accepts `message` (1..2000 chars), `vehicle_id` (nullable owned vehicle), `postal_code`, `specialty` (nullable), `mobile_only` (boolean). Returns `reply`, `intent` (`advice`, `find_provider`, `clarify`), `specialty` (nullable), `providers` (Provider[]), `videos` ({title, url, source}[]), and optional `answer_source: "AI guidance"` when a bounded model call succeeds. It never mutates a request or invents diagnosis, appointments or availability. Only nonurgent advice for nondemo customers may call the model, capped by a persistent 30 requests per customer per hour; deterministic fallback remains useful without AI keys or on errors. Tire-pressure questions carry a labeled [Michelin USA video](https://www.youtube.com/watch?v=dn0ShsQRgho).

`POST /v1/dev/session` exists only under explicit development/demo configuration, returns `access_token` and `demo:true`; it seeds fictional data for a single demo identity. Release-mode customer login uses Supabase; demo sessions are never accepted in production.

Bridge routes require a separate `X-Bridge-Key` and never accept customer tokens as authority. POST /v1/bridge/providers upserts an opt-in provider including `public_visible` and source IDs; `POST /v1/bridge/sync` also pulls the original Estimoto `GET /bridge/plus/providers` catalog, including opt-out rows, hides previously listed providers absent from the complete catalog, and pulls `GET /bridge/plus/requests/{id}` events bound by request ID, provider source ID, and durable receipt. Production estimate creation requires a successful fresh provider-catalog pull before delivery. The production background worker performs these pulls. POST /v1/bridge/requests/{id}/events accepts event_id, provider_id, status, message and optional scheduled_at, with replay protection and transition checks. Trusted estimate/repair snapshot endpoints bind records to an existing explicit customer/vehicle relationship; email/VIN cannot claim records. For a locally submitted estimate, the snapshot must additionally carry `estimate_id` and matching `provider_source_id`, and can only advance status. `ready`/`approved` require an authoritative amount. `processing_state=failed` is terminal for that immutable submission and exposes the receiver's safe `processing_error`; transient bridge outages leave processing retryable.

The estimate outbox POSTs to fixed `BRIDGE_ESTIMATE_URL` (`/bridge/plus/estimates`) with `Idempotency-Key: estimate:<estimate_id>` and frozen fields `estimate_id`, `customer_id`, `vehicle_id`, `provider_source_id`, `service_postal_code`, `discipline`, `description`, `claim_number`, `date_of_loss`, `contact` (name/email/phone/contact_preference), `vehicle` (year/make/model/VIN/mileage; insurance policy omitted), and `photos` (`id`, `capture_key`, `sha256`). The receiver returns a durable `{ "receipt_id": "..." }` only after saving its job/intake. It imports private bytes through fixed `GET /v1/bridge/estimates/{estimate_id}/photos/{photo_id}` with `X-Bridge-Key`; the Plus API verifies the frozen photo hash and never accepts a customer-supplied fetch URL. Later worker calls `POST /bridge/plus/estimates/{id}/process` until processing completes, then polls `GET /bridge/plus/estimates/{id}` for authoritative status. Each response must include explicit local estimate/customer/vehicle/provider binding and `source_id`, `status`, nullable `amount_cents`, `processing_state`, and nullable `processing_error`. The original assessor decides whether PDR evidence supports a real quote; Plus never invents a figure or approval.

Service-request durable outbox delivery POSTs to fixed `BRIDGE_REQUEST_URL` with `Idempotency-Key`; only a persisted upstream receipt counts as delivered. The creation payload freezes approved contact/vehicle fields and service ZIP. A cancellation tombstone may arrive before delayed creation: the receiver must persist it and neutralize any late creation before acknowledging. Both outboxes use database claim leases and retries. Production settings require dedicated PostgreSQL, Supabase Auth URL/publishable key, both fixed HTTPS bridge URLs, bridge key, mounted private photo volume, and `SOURCE_SHA`; `WORKER_ENABLED` defaults true in production and `WORKER_INTERVAL_SECONDS` defaults 15 (allowed 5–300). Optional `WEB_DIR` mounts the built Flutter web app at `/` after API routes. `GET /health/live`, `GET /ready` (database/migration/photo volume), and `GET /version` (`source_sha`) expose deployment state without secrets. The current migration enables row-level security and revokes Supabase Data API table access from `anon`/`authenticated`; the app connects as the private table-owning database role.
